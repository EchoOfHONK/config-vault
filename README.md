# Config Vault

Config Vault — самостоятельное хранилище конфигураций устройств и сервисов. Оно объединяет текущие файлы, неизменяемые версии, построчное сравнение, снимки и зашифрованные резервные копии. Для работы с интерфейсом знать Git не требуется: история отображается как «Версия 1», «Версия 2» и так далее. Восстановление старого содержимого создаёт новую версию и сохраняет последующие изменения в истории.

Приложение работает на вашем сервере. Содержимое конфигураций и SSH credentials не передаются внешним сервисам. Стек: React, TypeScript, Vite и CodeMirror; FastAPI/Python; PostgreSQL; Git для истории; Docker Compose и nginx.

PostgreSQL хранит metadata и неизменяемые зашифрованные версии; Git содержит дополнительную зашифрованную копию истории. При запуске приложение сверяет Git с версиями базы. Restore backup восстанавливает базу и строит историю из проверенных версий, включая повторное шифрование для нового ключа portable backup. Это позволяет восстановиться даже после сбоя между сохранением версии и записью её Git commit.

## Что можно делать

- Создавать устройства Server, PC, Laptop, NAS, Router, VPS, VM, Container Host, Console и Other с ручным, локальным или SSH подключением.
- Хранить текстовые конфигурации, относить их к сервисам и проектам, назначать теги и искать по имени, пути и содержимому.
- Импортировать отдельные файлы и архивы ZIP/TAR, вставлять текст, получать выбранные файлы через SSH.
- Редактировать конфигурации, просматривать историю, unified или side-by-side diff и восстанавливать версии после просмотра изменений.
- Создавать снимки устройства или выбранных конфигураций, восстанавливать отдельные файлы либо весь снимок.
- Обнаруживать внешние изменения через локальный watch или SSH sync, проверять конфликты перед применением и явно выбирать способ их разрешения.
- Управлять пользователями Admin, Editor и Viewer, ограничениями по устройствам/проектам/сервисам и API tokens.
- Создавать зашифрованные backup вручную и по расписанию, скачивать их и восстанавливать экземпляр.

В хранилище при установке нет демонстрационных устройств, файлов или истории. Счётчики на Dashboard отражают ваши данные.

## Установка на Debian

Нужны Debian 12/13 либо другой Linux с Docker Engine, Compose plugin с поддержкой `--wait` (либо standalone Docker Compose), Python 3.9+, Git и доступом к registry образов и пакетам Python/npm. Рекомендуется отдельная машина или VM, минимум 2 ГБ RAM, 4 ГБ для больших backup, и свободное место для базы, истории и резервных копий. На сервере заранее установите Docker по [официальной инструкции](https://docs.docker.com/engine/install/debian/). Не выставляйте PostgreSQL или backend напрямую в интернет.

Склонируйте [репозиторий Config Vault](https://github.com/EchoOfHONK/config-vault), перейдите в его каталог и запустите:

```sh
git clone https://github.com/EchoOfHONK/config-vault.git
cd config-vault
chmod +x install.sh update.sh backup.sh restore.sh
./install.sh
```

Репозиторий публичный: для клонирования авторизация GitHub не нужна. Если вы получили архив исходников, распакуйте его и выполните команды установки в каталоге с `docker-compose.yml`.

Установщик спрашивает HTTP-порт, адрес привязки, пустой каталог данных, отдельный каталог локального импорта, необязательный домен HTTPS, имя и пароль администратора, имя экземпляра и часовой пояс. Непустой каталог данных отклоняется: существующий экземпляр нужно запускать с его прежними настройками и ключом. Для reverse proxy оставьте `127.0.0.1`; для доступа из доверенной LAN можно явно выбрать `0.0.0.0`. Без HTTPS не открывайте порт в интернет.

Установщик создаёт `.env` и `.secrets/` с правами `0600`/`0700`; генерирует случайный пароль PostgreSQL и постоянный ключ шифрования. Пароль администратора используется один раз через `bootstrap.json`; после успешной проверки здоровья установщик очищает этот файл. Если запуск оборвался, проверьте `docker compose logs backend`, затем выполните `docker compose up -d --build --wait` и `python3 scripts/config.py clear-bootstrap` после успешного входа. Никогда не заменяйте ключ на существующем экземпляре.

Контейнер backend читает секреты при старте и запускает приложение с uid/gid `10001`; пользователь приложения не имеет прав root. PostgreSQL и backend доступны только внутри Compose network. Файлы локального импорта смонтированы **только на чтение**.

```sh
docker compose ps
docker compose logs --tail 100 backend
curl http://127.0.0.1:8080/api/health
```

Если указан домен, `COOKIE_SECURE=true`: вход работает через HTTPS. Для локального HTTP оставьте `COOKIE_SECURE=false`. Перезапуск после изменения `.env`: `docker compose up -d`.

## Первая настройка

При установке через `install.sh` администратор уже создан. Войдите под заданным именем. Для ручного развёртывания подготовьте секреты, `.env` и пустой `.secrets/bootstrap.json` с `{}`; при первом открытии интерфейс предложит создать администратора и задать имя экземпляра/часовой пояс. Размещение данных контролируется Docker mount, а не полем в браузере.

В Settings задайте интервал резервных копий и retention. Добавьте первое устройство в Devices, затем импортируйте первый файл в Import либо создайте конфигурацию вручную. Dashboard начнёт показывать реальные устройства, изменения и состояние backup. Для первой конфигурации выберите политику Manual либо Pull Only; разрешение на запись назначайте отдельно.

## Локальный сервер

Создайте Device с Connection `Local`. Разрешённый корень внутри контейнера — `/imports`; укажите его в roots устройства. Исходный каталог задаётся `LOCAL_IMPORT_DIRECTORY` в `.env` и монтируется в `/imports`.

Например, скопируйте разрешённые конфигурации в каталог локального импорта, сохранив структуру:

```sh
mkdir -p imports/nginx
cp /etc/nginx/nginx.conf imports/nginx/nginx.conf
```

У пользователя контейнера `10001:10001` должны быть права чтения файлов и прохода по каталогам. Для файлов с чувствительными данными используйте ACL или группу, а не общедоступные права. Не монтируйте весь `/`, Docker socket или `.ssh`. Watch отслеживает только доступные пути; при копировании файлов в staging каталог он наблюдает staging, а не исходный `/etc`.

Чтобы наблюдать настоящий `/etc/nginx`, задайте `LOCAL_IMPORT_DIRECTORY=/etc/nginx` и импортируйте `/imports/nginx.conf`. Это по-прежнему read-only подключение. Watch создаёт новые версии при внешних изменениях, но не выполняет reload автоматически.

Для локальной записи администратор должен сознательно предоставить writable mount в отдельном Compose override. Например:

```yaml
services:
  backend:
    volumes:
      - /srv/vault-managed-configs:/imports:rw
```

Не делайте системные каталоги writable без необходимости. Контейнеру также нужны права записи в файлы; vault не повышает привилегии для local apply. Для `/etc`, systemd и сервисных hooks практичнее ограниченная SSH учётная запись на целевой системе.

## SSH сервер

Создайте устройство с Connection `SSH`; задайте Host, Port, Username и разрешённые абсолютные roots, например `/etc/nginx` или `/srv/apps`. В Connection сохраните пароль либо private key и passphrase. Они шифруются ключом экземпляра. Предпочтительна отдельная учётная запись с минимальными правами.

Получите host key и сравните fingerprint с ключом, проверенным на самом сервере, например через `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`. Сохраните подтверждённый host key и нажмите Test Connection. Получение ключа из сети само по себе не доказывает подлинность сервера. Изменившийся host key блокирует подключение: выясните причину до повторного подтверждения.

В Import выберите устройство и каталог, просмотрите список и отметьте конкретные файлы. Symlinks, выход за разрешённые roots и чрезмерно большие файлы/архивы отклоняются. Импорт по SSH не записывает данные на удалённый сервер.

## Редактирование, версии и restore

Откройте Config: видны устройство, путь, формат, текущая версия и действия. Редактор поддерживает номера строк, подсветку, поиск/замену и folding для поддерживаемых языков. Сохранение всегда проверяет номер версии: изменение, выполненное другим пользователем, не перезаписывается незаметно.

Для JSON, YAML и TOML используется разбор формата. Другие форматы проверяются доступными специализированными или базовыми проверками. Невалидные данные нельзя применять на удалённый сервер. Перед remote apply Nginx и Compose проверяются соответствующими инструментами на целевой машине; установите там `nginx`/Docker Compose. Успешная базовая проверка текста не означает, что сервис обязательно запустится.

History содержит автора, время и комментарий каждого изменения. Выберите две версии для Compare. Restore сначала показывает diff с текущей версией и требует подтверждения. Например, восстановление версии 1 после версии 5 создаёт версию 6 «Restored from version 1», а версии 2–5 остаются в истории. Restore внутри Vault меняет сохранённое содержимое; запись на устройство требует отдельного Apply.

## Sync, конфликты и Safe Apply

Политики файла:

| Политика | Поведение |
| --- | --- |
| Manual | Изменения и действия инициирует пользователь. |
| Pull Only | Получение внешних изменений; запись запрещена. |
| Push/Pull | Явное применение после проверки версии и hash удалённого файла. |
| Watch | Наблюдение локального файла и создание версии при изменении. |
| Auto Backup Only | Сохранение внешнего состояния без автоматической записи. |

SSH Auto Sync включается на устройстве отдельно с интервалом. Sync читает файл и создаёт версию, если изменилось внешнее содержимое. Он не применяет Vault на remote автоматически. Автор внешнего изменения неизвестен, если нет достоверного источника этой информации; имя SSH пользователя не выдаётся за автора.

Ручная загрузка или вставка текста не подтверждает привязку к файлу на устройстве. Такой файл не участвует в автоматическом Sync/Watch, пока пользователь с правами на устройство явно не выполнит Sync. Импорт из Local/SSH сразу фиксирует проверенный источник. Редактор, ограниченный проектом или сервисом, может работать с уже подтверждёнными источниками своей группы, но не получает произвольный доступ через сохранённые SSH credentials.

После редактирования сохраните версию в Vault, затем используйте Apply. Система заново проверяет remote hash и текущую версию, валидирует кандидат и только после этого записывает его. Если Vault и remote изменились одновременно, появится Conflict: сравните стороны и выберите Keep Remote, Keep Vault либо Merge Manually. Keep Vault/ручной результат означает явную запись после повторной проверки. При новой гонке потребуется повторный просмотр.

Hooks отключены по умолчанию. Admin может включить только предусмотренные команды: reload nginx, Docker Compose up, systemd daemon-reload. Браузер не позволяет передать произвольную команду. Перед запуском пользователь видит действие и явно включает его; выполнение и результат записываются в audit. Нужны соответствующие права SSH пользователя. Локальный Docker контейнер не управляет systemd хоста.

## Снимки, сервисы и проекты

Snapshot сохраняет ссылки на конкретные версии выбранных конфигураций. Назовите снимок, например «Перед обновлением Debian», и укажите устройство либо список файлов. Восстановление создаёт новые версии выбранных файлов; проверка ожидаемых текущих версий предотвращает потерю параллельных изменений. Весь выбранный набор восстанавливается одной транзакцией. Применение на remote выполняется отдельно для соответствующих файлов.

Services группируют конфигурации приложения; Projects объединяют связанные файлы нескольких устройств. Теги помогают искать production, vpn, docker и другие группы. В Compare можно сопоставить устройства по путям конфигураций. Проект можно экспортировать как архив обычного Git repository; вероятные secrets маскируются, а `.gitignore` исключает стандартные секретные файлы.

## Secrets и права

Подозрительные значения PASSWORD, TOKEN, API_KEY, SECRET, PRIVATE_KEY и Authorization скрываются по умолчанию, включая `.env` и search preview. Editor/Admin может раскрыть содержимое для редактирования; это действие записывается. Детектор эвристический: нестандартный секрет может потребовать ручного внимания. Экспорт и публикацию всегда проверяйте.

Admin управляет экземпляром, пользователями, credentials и hooks. Editor меняет разрешённые конфигурации; Viewer просматривает доступные данные без изменения и раскрытия секретов. Ограничения назначаются по Device, Project или Service; пользователь не получает доступ ко всем остальным объектам. Нельзя удалить или понизить последнего администратора.

Если списки разрешённых устройств, проектов и сервисов пусты, роль имеет доступ ко всему экземпляру; для ограниченного пользователя обязательно выберите нужные объекты. Шаблоны общие для экземпляра: вероятные secrets в них маскируются, раскрыть исходные секретные значения может только Admin. Для обычного использования шаблона замените скрытые значения своими.

API tokens выдаются один раз и хранятся как hash. Доступные permissions: `read:configs`, `write:configs`, `sync:device`, `create:snapshot`; дополнительно ограничьте устройства и срок действия. Для внешнего клиента передавайте `Authorization: Bearer TOKEN`. Cookie клиенты отправляют `X-CSRF-Token` для запросов, изменяющих состояние. Машиночитаемая OpenAPI схема доступна на `/api/openapi.json`; основной REST API расположен под `/api`.

Запись audit включает входы, просмотр/раскрытие конфигураций, изменение, restore, snapshot, sync, apply, hooks, backup и изменения пользователей. Не храните комментарии с паролями и tokens. Просматривайте Activity при расследовании изменений.

## Backup

Backup содержит данные PostgreSQL логического уровня, пользователей и права, устройства, metadata, версии, снимки, audit, настройки и Git историю. Архив зашифрован; SSH credentials и конфиги не появляются в открытом виде. Прямое копирование только `/data/vault` не заменяет полный backup.

Ручной backup через интерфейс создаёт зашифрованный файл и позволяет скачать его. Settings управляет интервалом и retention для планировщика. Для согласованной offline копии используйте:

```sh
./backup.sh
```

Скрипт кратковременно останавливает backend/frontend, оставляет PostgreSQL работающим, запускает тот же backup engine, копирует архив в доступный владельцу каталог `<DATA_DIRECTORY>/backups/` с правами `0600` и возобновляет сервисы. Внутренняя копия остаётся в `<DATA_DIRECTORY>/vault/backups/`. Retention относится к копиям внутри приложения; CLI экспорт не удаляется планировщиком. Храните отдельные внешние копии и регулярно проверяйте восстановление.

По умолчанию backup открывается только ключом `.secrets/vault_key`. Сохраните его отдельно от сервера и backup, в защищённом offline месте. Для переносимого backup задайте отдельный длинный пароль в файле с правами `0600`:

```sh
umask 077
python3 -c 'import getpass; from pathlib import Path; Path("backup-password").write_text(getpass.getpass("Пароль backup: "))'
./backup.sh --portable "$(pwd)/backup-password"
```

Переносимая копия позволяет восстановиться с новым ключом экземпляра: содержимое повторно шифруется текущим ключом. Не храните файл пароля вместе с архивом. Не удаляйте старый ключ до проверки всех старых непереносимых копий.

## Disaster recovery на новой машине

1. Установите Docker/Compose/Python и получите тот же релиз Config Vault.
2. Для обычного backup восстановите `.secrets/vault_key` из защищённой копии; остальные секреты PostgreSQL можно сгенерировать заново. Для portable backup подготовьте файл его пароля — старый ключ не обязателен.
3. Запустите `./install.sh` на пустом каталоге данных. Для обычного backup замените только что созданный ключ сохранённым ключом **до** восстановления и пересоздайте backend: `docker compose up -d --force-recreate backend`. Новый экземпляр временно содержит только администратора установки.
4. Скопируйте backup на новую машину и выполните `./restore.sh /путь/backup.cvbackup`, либо `./restore.sh /путь/backup.cvbackup /путь/backup-password` для portable backup. Введите `RESTORE`. Перед заменой работающего хранилища скрипт делает дополнительный backup. Restore выполняется при остановленном приложении.
5. После восстановления войдите учётной записью из backup, проверьте Devices, Configurations, History, Snapshots, Users и Activity. Укажите актуальные SSH адреса, локальные mounts и домен; выполните Test Connection и Sync. Не запускайте Apply сразу после переезда без сравнения remote.
6. Создайте новую внешнюю копию и проверьте её на изолированном экземпляре.

Восстановление заменяет хранилище, а не объединяет два экземпляра. При ошибке restore сервисы остаются остановленными; изучите ошибку и восстановите последнюю исправную копию. Не используйте `docker compose down -v` и не удаляйте рабочий каталог данных для обычного обновления или проверки.

## Обновление

```sh
./update.sh
```

Сначала создаётся backup; затем в отдельном Git checkout выполняется только fast-forward pull, пересборка контейнеров и проверка здоровья. Если исходники изменены локально, pull не выполняется. Для поставки архивом предварительно замените исходники новым релизом, сохранив `.env`, `.secrets` и каталог данных, затем запустите скрипт. Данные не удаляются.

Перед сменой релиза читайте его совместимость схемы и инструкции миграции; текущая версия инициализирует свою схему при старте. Для отката верните исходники совместимого релиза и восстановите backup, созданный перед обновлением. Не запускайте старый backend на неподдерживаемой новой схеме.

## Nginx reverse proxy и HTTPS

Пример для внешнего nginx расположен в `deploy/nginx-reverse-proxy.conf`. Замените домен, сертификат и порт; получите действительный TLS сертификат вашим обычным способом. Config Vault размещается в корне отдельного домена, например `https://vault.example.org/`.

```sh
sudo nginx -t
sudo systemctl reload nginx
```

В `.env` задайте `COOKIE_SECURE=true`, оставьте `BIND_ADDRESS=127.0.0.1` и перезапустите контейнеры. Proxy передаёт Host с исходным портом и `X-Forwarded-Proto: https`; лимит upload для восстановления backup — 512 МБ, timeout — 300 секунд. Встроенный nginx отдаёт CSP, запрет framing, MIME sniffing и referrer. Внешний HTTPS proxy включает HSTS. Переданный клиентом `X-Forwarded-For` заменяется адресом соединения: подделка этого заголовка не обходит rate limit. За дополнительным proxy несколько пользователей могут учитываться под одним IP; точное определение IP требует nginx `real_ip` с явно ограниченным доверенным proxy, а не доверия произвольным заголовкам. Не выставляйте `/api` отдельно с другими cookie/origin и не отключайте CSRF. Временные upload файлы backend хранятся в защищённом дисковом `<DATA_DIRECTORY>/vault/tmp/`, а не в ограниченном RAM tmpfs.

## Разработка и тесты

Backend требует Python 3.12. Production использует PostgreSQL; SQLite допускается только в изолированных тестах. Frontend требует Node.js 22 и pnpm 11.19.0, закреплённый в `packageManager`:

```sh
python3 -m venv backend/.venv
backend/.venv/bin/pip install -r backend/requirements.txt
cd frontend
corepack enable
pnpm install --frozen-lockfile
pnpm build
cd ../backend
.venv/bin/pytest -q
```

Проверки API покрывают CRUD, версии, diff, restore, snapshots, права, secrets, validation, backup/recovery и remote workflow. Для настоящего SSH integration target есть `scripts/ssh-fixture.sh`: он запускает отдельный Debian 13 контейнер с реальным OpenSSH и nginx, случайным тестовым паролем и только вашим тестовым каталогом `/fixtures`. Root/password login разрешён **только внутри одноразового fixture**, а порт привязан к loopback. Он не является production SSH конфигурацией. После проверки удалите контейнер.

CI запускает backend tests, production frontend build, shellcheck и Debian SSH fixture. Для полной проверки Docker deployment используйте сценарий `scripts/verify-debian.sh`; он создаёт отдельный Compose project, выполняет реальные операции API и проверяет восстановление после удаления **только тестовых** application data. Результаты конкретного запуска фиксируются отдельно; наличие сценария не означает, что он уже выполнен на вашей машине.

Результат уже выполненного сценария этой поставки и точные границы проверки: [VERIFICATION.md](VERIFICATION.md).

## Границы текущей поставки

Secrets Hub — будущая интеграция: сейчас credentials шифруются локально, автоматического переноса во внешний vault нет. Полноценный Windows/Linux агент не поставляется; REST API и ограниченные tokens готовы для отдельного клиента. Compare сопоставляет сохранённые конфигурации, а не инвентаризирует версии установленных пакетов. Нет произвольного выполнения команд, автоматического разрушительного merge или автоматической публикации secrets в GitHub/GitLab. Экспорт проекта даёт локальный архив repository для дальнейшего самостоятельного push.

Local Watch наблюдает смонтированные доступные файлы из контейнера. SSH sync опрашивает устройство по расписанию; достоверное определение автора внешней правки требует журнала целевой ОС, которого обычный SSH read не предоставляет. Встроенные текстовые проверки systemd/WireGuard не заменяют запуск сервиса на целевой системе. Ограничения: текст конфигурации до 1 МиБ; импорт до 20 МиБ; внутренний сжатый payload backup до 256 МиБ (зашифрованный файл больше из-за кодирования). Восстановленный каталог backup сохраняет записи старых копий как архивные: сами внешние файлы нужно хранить отдельно.
